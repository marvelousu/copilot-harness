# 1,900 クレジット運用

## 課金の形

2026年6月1日から、Copilot は従量課金になった。使用量はトークンで測られ、GitHub AI Credits に換算される。1クレジットは 0.01 ドル。Business プランに含まれるのは 1ユーザーあたり月 1,900 クレジットで、金額にすると 19 ドル分のトークンにあたる。

課金されるものとされないものがはっきり分かれている。

| 機能 | 課金 |
|---|---|
| コード補完、Next Edit Suggestions | されない |
| チャット | される |
| エージェントモード | される |
| コードレビュー、PR サマリ | される |

**トークン従量なので、文脈の大きさがそのまま金額になる。** リクエスト単価の話ではなく、毎回送る文脈の総量で決まる。以下はすべてこの一点から導かれる。

## 実測で分かった優先順位

Copilot CLI 1.0.83 で計測した結果、削る順序は当初の想定と逆だった。詳しい数値は `docs/verified-on-cli.md`。

**指示ファイルはキャッシュの外に載り、MCP のツール定義はキャッシュの中に載る。** キャッシュ済みトークンは桁違いに安いので、同じトークン数でも指示ファイルのほうがずっと高い。指示ありと指示なしで総入力量はほぼ同じなのに、費用は3倍違った。

したがって、まず指示ファイルを削り、MCP は3本程度に抑えるだけでよい。MCP を全部止めても費用は13%しか下がらない。

もう一つ、**指示やスキルを書き換えるとキャッシュが無効になり、次の実行が初回価格になる。** 頻繁にいじらない。

## 効く順

### 1. 補完で済むものをチャットに投げない

補完と Next Edit Suggestions は課金対象外で、上限もない。変数名の変更、定型的な分岐の追加、import の補完はチャットに投げるとその都度トークンを払う。手で書き始めて補完に任せるほうが速くて無料になる。

### 2. MCP サーバを常時全部つながない

エージェントモードは有効なツールの定義をすべて文脈に読み込む。実測で、ツール定義だけで文脈の約25パーセント、10万トークン中およそ2万5千トークンを占める。VS Code のエージェントモードにはツール128個の上限もあり、サーバを増やすと上限に当たって使えなくなる。

常時オンは2つまでにする。残りは使うときだけツールピッカーで入れる。

| サーバ | 運用 |
|---|---|
| github | 常時オン |
| context7 | 常時オン |
| playwright | ブラウザ操作をする作業のときだけ |
| playwright-ext | 既存ログイン済みブラウザが要るときだけ |
| windows-mcp | デスクトップ GUI 操作をするときだけ |

VS Code 1.104 以降はツール検索が入っており、常時利用可能な約30個の中核ツールと、必要になるまでスキーマを読み込まない遅延ツールに分かれる。これで最大20パーセント削減されるが、サーバを絞る効果のほうが大きい。

### 3. 指示ファイルを小さく保つ

`.github/copilot-instructions.md` は全リクエストに載る。ここに手順を書くと、その手順を使わないリクエストでも毎回払う。手順は `.github/skills/` に置く。スキルは関連するときだけ読み込まれる。

`AGENTS.md` と `.github/copilot-instructions.md` の両方に同じ内容を書かない。両方読まれるので二重に払うことになる。

### 4. 話題ごとに新しいチャットを開く

スレッドは毎ターン履歴全体を送り直す。1つのスレッドで話題を変え続けると、無関係な過去のやり取りにずっと課金される。作業が変わったら新しいチャットにする。

### 5. 探させずに渡す

対象ファイルが分かっているなら添付する。エージェントにリポジトリ全体を検索させると、読んだファイルが全部文脈に入る。「このバグを直して」より「このファイルのこの関数を直して」のほうが安い。

### 6. モデルを作業で使い分ける

推論の重いモデルは思考過程のトークンも課金対象になるため、同じ作業で数倍消費する。計画とレビューには使う価値があるが、機械的な変換や定型的な実装に使うと丸損になる。

手で選び続けるのは続かないので、カスタムエージェントの frontmatter に `model:` を書いて固定する。このリポジトリでは `implementer` を中位、`reviewer` を上位、`mechanical` を下位に割り当てる前提で作ってある。モデル名は組織の契約で変わるためコメントアウトしてあり、導入時に埋める。手順は `docs/model-routing.md`。

判断の分かれ目は「選択肢を比較する必要があるか」。比較が要るなら上位、写経に近いなら下位にする。実装の回数は計画の回数より一桁多いので、ここを下げると効く。

## CLI の制御フラグ

| フラグ | 用途 |
|---|---|
| `--max-ai-credits <n>` | セッションあたりの上限。暴走の保険 |
| `--usage-output-file <f>` | 使用量を JSON で出す。作業単位の実測に使う |
| `--effort <level>` | 推論の深さ。none から max |
| `--context <tier>` | `default` で足りるなら `long_context` に上げない |

## 月内の見張り方

- 週の初めに消費を確認する。1,900 クレジットを4週で割ると週475が目安になる。
- 超過分は従量で課金される。上限を設定していない場合は青天井なので、管理者に予算上限の設定を確認する。
- 使い切りそうなときに最初に削るのは、エージェントモードの探索作業。手で場所を特定してから頼むと大きく減る。
