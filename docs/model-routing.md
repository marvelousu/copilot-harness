# モデル振り分け

トークン従量課金では、同じ作業でもモデルによって消費が桁で変わる。単価は CLI が起動時に取得する `/models` 応答に載っており、デバッグログから読める。Business で使える主なモデルを出力単価の高い順に並べる。単位は応答に書かれた100万トークンあたりの値で、絶対額よりも比率を見る。

| モデル | 区分 | 入力 | キャッシュ読み | キャッシュ書き | 出力 |
|---|---|---|---|---|---|
| claude-fable-5.1 | very_high | 1000 | 25 | 1250 | 5000 |
| gpt-6-astra | very_high | 1000 | 100 | 1250 | 5000 |
| gpt-5.5 | high | 500 | 50 | 0 | 3000 |
| claude-opus-5 | high | 500 | 50 | 625 | 2500 |
| gpt-5.6-sol | high | 400 | 40 | 500 | 2000 |
| gpt-5.4 | medium | 250 | 25 | 0 | 1500 |
| gpt-5.6-terra | medium | 200 | 20 | 250 | 1200 |
| claude-sonnet-5 | medium | 200 | 20 | 250 | 1000 |
| gpt-5.4-mini | low | 75 | 7.5 | 0 | 450 |
| gemini-3.8-flash | low | 75 | 7.5 | 0 | 375 |
| gpt-5.6-luna | low | 20 | 2 | 25 | 120 |

読み取れることが3つある。

- **段の差は10倍単位。** luna は terra の10分の1、opus-5 の25分の1、fable-5.1 の50分の1。実装作業を luna に落とすと、その作業の費用は一桁下がる。
- **出力は入力の5倍から6倍。** 長い説明や大量のコード生成は入力の何倍も課金される。「要点だけ」と指示するのは礼儀でなく節約になる。
- **キャッシュ読みは入力の10分の1。** 同じ文脈を送り直す分は安い。逆に、指示ファイルのようにキャッシュの外に載る部分は10倍払っている。

## 方針

| 作業 | 段 | テンプレートの値 |
|---|---|---|
| 設計、計画、案の比較 | 上位 | gpt-5.6-sol |
| レビュー、ゲート判定 | 上位 | gpt-5.6-sol |
| 原因不明のバグ調査 | 上位 | gpt-5.6-sol |
| 方針が決まった実装 | 中位 | gpt-5.6-terra |
| 一括リネーム、定型変換、boilerplate | 下位 | gpt-5.6-luna |
| コミットメッセージ、docstring | 下位 | gpt-5.6-luna |

判断の分かれ目は「選択肢を比較する必要があるか」。比較が要るなら上位、写経に近いなら下位。

Claude で組むなら上位が `claude-opus-5`、中位が `claude-sonnet-5`。下位に相当する Claude は Business の一覧に見当たらないので、そこだけ `gpt-5.6-luna` を使う。

## CLI での入れ方

`~/.copilot/settings.json` で既定モデルとエージェント別モデルを固定する。`templates/copilot-cli-settings.json` がその雛形で、`model` が既定、`subagents.agents.<エージェント名>` が `--agent <名前>` で呼ぶカスタムエージェントの指定になる。`effortLevel` で推論の深さ、`contextTier` で文脈枠も一緒に決められる。

```json
{
  "model": "gpt-5.6-terra",
  "subagents": {
    "agents": {
      "reviewer":    { "model": "gpt-5.6-sol",   "effortLevel": "high" },
      "implementer": { "model": "gpt-5.6-terra", "effortLevel": "medium" },
      "mechanical":  { "model": "gpt-5.6-luna",  "effortLevel": "low" }
    }
  }
}
```

この振り分けは実機で確認済み。既定と `--agent reviewer` で別のモデルが使われた。

**存在しても契約で使えない名前を書くと、黙って `mai-code-1.1-flash` に落ちる。** エラーは出ず、ログに警告が残るだけである。設定を入れたら `copilot -p "Reply with OK" --usage-output-file u.json` を実行し、`modelMetrics` に意図した名前が出ることを確認する。

一時的に変えるときは `--model <name>` と `--effort <level>` を使う。`--model` に使えない名前を渡した場合はエラーで止まる。`auto` で自動選択になる。

## VS Code での入れ方

カスタムエージェントの frontmatter に `model:` を書くと、そのエージェントを選んだときのモデルが固定される。

```yaml
---
name: implementer
description: 方針が決まった実装タスクの担当。
model: <モデル名>
---
```

**このリポジトリでは `model:` をコメントアウトしてある。** VS Code のモデルピッカーに出る名前は CLI の名前と一致するとは限らず、存在しない名前を書くとエージェントが動かなくなるためである。ピッカーに表示された名前をそのまま使う。`model:` が解決するのは Copilot 提供のモデルだけで、独自エンドポイントのモデルは指定できない。

プロンプトファイルの frontmatter でも `model:` を指定できる。計画とレビューだけ上位に固定し、既定は中位にしておくと、意識せずに振り分けが効く。

## 効果の見積もり

上位モデルを使う場面を計画とレビューに限定すると、日常の実装作業がすべて中位以下に落ちる。実装の回数は計画の回数より一桁多く、単価も一桁違うので、ここが最も効く。
