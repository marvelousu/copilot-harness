# モデル振り分け

トークン従量課金では、同じ作業でもモデルによって消費が数倍変わる。推論の重いモデルは思考過程のトークンも課金対象になるため、単純作業に使うと丸損になる。

## 方針

| 作業 | モデル |
|---|---|
| 設計、計画、案の比較 | 上位モデル |
| レビュー、ゲート判定 | 上位モデル |
| 原因不明のバグ調査 | 上位モデル |
| 方針が決まった実装 | 中位モデル |
| 一括リネーム、定型変換、boilerplate | 下位モデル |
| コミットメッセージ、docstring | 下位モデル |

判断の分かれ目は「選択肢を比較する必要があるか」。比較が要るなら上位、写経に近いなら下位。

## 仕組みへの入れ方

カスタムエージェントの frontmatter に `model:` を書くと、そのエージェントを選んだときのモデルが固定される。これが最も確実な振り分け方法で、毎回手で選ぶ必要がなくなる。

```yaml
---
name: implementer
description: 方針が決まった実装タスクの担当。
model: <モデル名>
---
```

**このリポジトリでは `model:` をコメントアウトしてある。** 利用できるモデル名は組織の契約とバージョンによって変わり、存在しない名前を書くとエージェントが動かなくなるためである。導入時に自分の環境で確認して埋める。

確認方法は、VS Code のチャットでモデルピッカーを開き、表示された名前をそのまま使う。CLI では `--model <name>` で指定し、`auto` にすると自動選択になる。実測では既定で `gpt-5.6-luna` が選ばれた。`model:` が解決するのは Copilot 提供のモデルだけで、独自エンドポイントのモデルは指定できない。

## 埋めるところ

| ファイル | 想定 |
|---|---|
| `.github/agents/implementer.agent.md` | 中位モデル |
| `.github/agents/reviewer.agent.md` | 上位モデル |
| `.github/prompts/plan.prompt.md` | 上位モデル |

プロンプトファイルの frontmatter でも `model:` を指定できる。計画とレビューだけ上位に固定し、既定は中位にしておくと、意識せずに振り分けが効く。

## 効果の見積もり

上位モデルを使う場面を計画とレビューに限定すると、日常の実装作業がすべて中位以下に落ちる。実装の回数は計画の回数より一桁多いので、ここが効く。
